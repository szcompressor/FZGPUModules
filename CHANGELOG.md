## [Unreleased] — 2.0.0

### Fixed
- **`QuantizerStage<double, …>` quantized at float32 precision, silently violating the error bound on f64 fields.** All four ABS/NOA forward kernels rounded with an unconditional `__float2int_rn(static_cast<float>(x) * static_cast<float>(ebx2_r))`, and the inverse reconstructed through a `float` — so `TInput = double` was nominal: the stage is templated and instantiated for `double`, but the arithmetic was never wider than f32. Any f64 field whose range is small next to its offset is unrepresentable that way. S3D/N2 spans 1.10e-5 about 0.7369, where the float32 spacing (5.96e-08) is **54x** the `abs_eb` a 1e-4 NOA bound asks for (1.103e-09) — the rounding error alone blew the bound before quantization did any work. Four cells (`cuszp2`/`cuszp3` x {plain, outlier}) round-tripped S3D/N2 at 48 dB with `status: ok` and `err_over_bound` **81.08 on all four**, the identical figure being the tell that the shared quantizer, not the coders, was at fault. Observed `max_abs_err` 8.941e-08 ~ 1.5x the float32 spacing, i.e. two roundings. Kernels now round via `quantRound<TInput>` (`__double2int_rn` for f64) and compare/reconstruct in `TInput`; `fabsf` on the threshold check was the same downcast and is gone. **Reachable only in `linear_mode`** — the radius-clamped path needs `|x|/abs_eb < 2*quant_radius` for an inlier, which forces `abs_eb` above the f32 spacing at `|x|`, so the radius check always escalates to an outlier first. That is why the cuSZp-style presets were hit and the others were not. The bound is also carried at full precision now: `computeValueBase()` returns `TInput` instead of narrowing the NOA range to `float`, and `QuantizerConfig` gained `abs_error_bound_f64` / `value_base_f64`, because decode computes `recon = q * 2*abs_eb` with `q ~ 3.3e8` — a 6e-08 *relative* error in a float `abs_eb` lands as 4.4e-08 absolute, 40x the bound. Old headers (<= 56 B) leave the new fields 0 and fall back to the float copies. **Throughput is unchanged**: the kernel is memory-bound, and a 64 Mi-element probe over f32/f64 x linear/radius x ABS/NOA moves every case by under 1.2%, within run-to-run noise (f64 linear NOA 0.4943 -> 0.4941 ms; f32 linear ABS 0.2275 -> 0.2271). Tests `QuantizerLinear.DoubleTinyRangeLargeOffsetRespectsBound` (fails at 61.4x over bound without the fix) and `QuantizerNOA.RefusesBoundBelowInputTypeSpacing`.
- **`LorenzoQuantStage` narrowed a computed f64 error bound to float32 twice, violating the bound on relative-mode f64 fields.** Its quantization kernel was already correct (`round(input[i] * ebx2_r)` in `TInput`), but the bound reaching that kernel was not: `computeValueBase()` returned `float`, so `abs_eb = user_eb * value_base` was formed from a narrowed range, and `LorenzoQuantConfig::error_bound` then serialized the result as a `float`, so the decompressor read back a bound with ~6e-08 relative error. **Only reachable in a relative mode** — under `ABS` the bound comes straight from `config_.error_bound`, which is already a `float`, so the header narrowing is a no-op there and an ABS test passes vacuously. `cusz` on S3D/N2 (f64, values ~0.7369, range 1.10e-5) at a 1e-4 `rel_range` bound came back **22.73x over bound at 53.27 dB with `status: ok`**. Both narrowings are independently causal, isolated by reverting one at a time on the real cell: with neither fix 22.73x / 53.27 dB, with only the `TInput` value_base **6.62x / 64.98 dB**, with both **1.0x / 84.75 dB**. `computeValueBase()` now returns `TInput`, `computed_value_base_` is `TInput`, and the header carries `error_bound_f64` / `value_base_f64` (pre-2026-08-08 headers leave them 0 and fall back to the float copies). The v2-field check now compares against the literal 44-byte v2 size instead of `sizeof(LorenzoQuantConfig)`, which the new fields would otherwise have pushed past every existing archive. Test `LorenzoQuantHeader.DoubleNoaTinyRangeLargeOffsetRespectsBound` — a **file** round-trip, deliberately: an in-process compress/decompress reuses the live stage object and never reads the serialized header, so it cannot observe this at all. Fails at 11.9x over bound without the fix.
- **Relative error-bound modes accepted bounds no implementation could satisfy.** NOA/PREL derive `abs_eb = eb * value_base`, which can land below the input type's own resolution at the data's magnitude — the input's round-trip error through `TInput` then exceeds the bound before any compression happens. `QuantizerStage` and `LorenzoQuantStage` now compare `abs_eb` against `epsilon(TInput) * max(|data|)` (the scan already had `max(|data|)`; `computeValueBase()` just discarded it) and throw rather than emitting a stream that decodes cleanly into out-of-bound values.
- **`setColoringEnabled(false)` was silently discarded by any later `setMemoryStrategy()` call, so it was a no-op for every TOML-loaded pipeline.** `setMemoryStrategy()` replaces `dag_` wholesale and re-applies Pipeline-level DAG state to the replacement, but it only ever restored `profiling_enabled_` — the exact hazard its own comment warns about ("Anything else added to CompressionDAG that is configured before finalize() must be re-applied here too"). Every preset carries a `memory_strategy` key, so `loadConfig()` routes through `setMemoryStrategy()`, and a caller doing the documented `setColoringEnabled(false)` → `loadConfig()` sequence got coloring left on. The failure mode was a **plausible wrong number, not an error**: a colored-vs-uncolored peak-memory sweep over all 15 presets reported exactly 0 bytes saved everywhere, reading as "liveness coloring contributes nothing" when coloring had simply never been disabled. With the flag restored, the same sweep shows 0–36% peak reduction depending on topology (pfpl 155.5→106.0 MB, quantizer_lorenzo_bitpack 103.8→66.7, cuszp2 76.9→52.1; fzgpu/lorenzo_bitpack/cuszp3_fixed genuinely 0). Fixed by mirroring the flag on `Pipeline` (`coloring_enabled_`) and re-applying it alongside `profiling_enabled_`. Regression test `BufferColoring.DisabledSurvivesMemoryStrategyChange`. Note the existing `BufferColoring.DisabledWhenRequested` passed throughout — it sets the flag on a hand-built pipeline that never calls `setMemoryStrategy()`, which is why the no-op went unnoticed.
- **`examples/presets/speed.toml` could not run at all — it wired its stages with `input_port`, a key the TOML parser does not recognize.** `config.cpp` reads stage wiring only from the `inputs = [{from = ..., port = ...}]` array; unknown keys are silently ignored, so both `bshuf` and `rze` were left unconnected and the preset failed at compress with `pipeline has 3 source stage(s); only single-source pipelines are supported`. The error names a topology problem, so it reads as a broken pipeline design rather than a typo'd key, and nothing in the load path warns that `input_port` was dropped. Only this preset was affected (`grep` for `input_port` across all TOMLs returns it alone); the other 14 presets all load and run. The C++ `fzgmod-profile-speed` target and `examples/toml_config.cpp` build the same Quantizer → Bitshuffle → RZE topology programmatically, which is why the preset's breakage never surfaced in profiling or examples. Rewired to `inputs`; now round-trips CLDHGH at 2.84× / 74.96 dB, identical under both memory strategies, `compute-sanitizer --tool memcheck` clean over `-b --runs 6`.
- **`--stages` rejected `gpulz` in its own error message, and a malformed `tupl` suffix crashed with `stoi`.** The "Unknown stage" message listed neither `gpulz[1|2|4|8]` (accepted since the GPULZ stage landed) nor `none`, so a user correcting a typo was told a valid stage was unsupported; `--help` was already correct, only the error path was stale. Separately, `tupl<dim>_<word>` parsed both fields with a bare `std::stoi`, so a non-numeric suffix like `tuplx_y` escaped as an uncaught `std::invalid_argument` whose `what()` is just `"stoi"`; it now reports the same expected-format guidance as the missing-underscore case.
- **`docs/config_file.md` documented `Lorenzo1D` / `Lorenzo2D` / `Lorenzo3D`, none of which are accepted `type` strings.** The registry matches `type` exactly and only ever had `LorenzoQuant`, so the page's own "complete example" would have thrown on load. Heading, example, and the Limitations stage list corrected; the latter now points at `--list-stages` rather than restating a list that goes stale.
- **The inverse DAG shrank a sink buffer below what its stage writes, silently losing whole chunks of data.** `buildInverseDAG()` propagated each stage's `estimateOutputSizes()` and then **overrode** every source's result buffer with "the exact per-source uncompressed size" from the archive. That size is exact for what the sink stage *reports*, not for what it *writes*: GPULZ zero-pads a partial tail chunk and its decode kernel writes the whole padded extent, then reports the pre-padding size so downstream element counts stay right (its inverse `estimateOutputSizes()` says so in as many words). Overriding with the smaller number left the decode kernel writing past its buffer, and under PREALLOCATE the region behind it is the *input compressed buffer* — so the tail chunk's write raced the other chunks' reads of that same stream and they decoded to garbage. The symptom pointed nowhere near the cause: whole chunks came back **zero-filled**, spread across the file rather than at the tail, with exit code 0 and no warning. CESM-2D `qcodes/PRECT` lost 14,480 B across 372 of 6,329 chunks; sibling fields of identical size were clean, because the discriminator is data (how many chunks take the coded path), not geometry. Now takes `max(estimate, exact size)`, which keeps the exact size wherever the estimate is smaller — its original purpose — without ever undercutting the stage. Requires an input length that is not a multiple of `chunk_size`, which is why every chunk-aligned test passed. Regression test `CLI/GpulzUnpaddedInputFileRoundTripIsLossless`: it needs separately-built compress and decompress DAGs, a pool-managed decompress output, and megabytes of data, and it is **deterministic only under `ctest --preset compute-san`** (31 invalid global writes without the fix, 0 with) — in-process the pool rarely lands the overrun somewhere that changes the answer.
- **`GPULZStage::estimateOutputSizes()` under-reserved on a partial tail chunk, so the encode wrote past its own buffer.** `execute()` zero-pads a non-multiple input up to `n_chunks * chunk_size` and encodes the tail as a *full* chunk, but the bound was computed from the unpadded input size — short by exactly the tail padding. Measured overruns of 4–40 B (1 MB input, `chunk_size = 2048`: 4-byte tail -> 12 B over, 512 -> 28, 1024 -> 40; exact multiples -> 0). Whether it faulted depended on pool slack, which made it look intermittent: as a *terminal* stage it surfaced as `cudaMemcpyAsync failed: invalid argument` in `Pipeline::writeToFile()` (2 of 3 identically-sized CESM-2D fields failed), but **mid-pipeline it exited 0 while still writing into whatever the pool had placed after the buffer**. Both branches now bound against the padded extent; the split-mode `literals` port had the same latent defect (a raw-fallback tail chunk contributes `chunk_size` bytes) and is fixed with it. The existing suite passed 48/48 because every GPULZ test helper padded to a chunk multiple *before* calling `estimateOutputSizes()` — the one shape that breaks it was never constructed. Five tests added covering unpadded inputs across all three chunk sizes, all four word sizes, and both split modes, asserting both the reported size and a canary region past the declared bound. Audited the other chunked coders: RRE/RZE/CLOG/HCLOG/RARE/RAZE all *clamp* the tail (`in_size = min(CS, total - off)`) and never emit more than `in_size`, so their bounds are exact; AdaptiveBitpack and BitplaneRZE size through padding-aware `configure()`/`maxArchiveBytes()`. GPULZ was the only stage that padded rather than clamped, and the only one affected.
- **`.fzm` archives were not byte-reproducible: the FZM header structs wrote uninitialized tail padding to disk.** `FZMBufferEntry`'s named members end at byte 250 but `sizeof` is 256 (8-byte alignment), and the constructor zeroed only the named arrays — so 6 bytes of stack garbage per buffer entry went straight into the file, along with the `header_checksum` computed over them. Two compressions of CESM-2D/CLDHGH through `gpu_zstd_lossless.toml` produced archives differing in exactly 12 bytes: 2 padding bytes in each of 4 buffer entries plus the 4-byte checksum. Round-trip was never affected (the padding is never read back), which is why it survived — but it defeats byte-for-byte reproducibility, and downstream tooling records a per-run `compressed_sha256` and compares baselines across machines on exactly that. Both `FZMStageInfo` and `FZMBufferEntry` now `memset` the whole object before assigning fields. Verified: 6 consecutive compressions now yield one hash where they previously yielded two.

- **The concat `gather_kernel` used one block per segment, collapsing on uneven splits.** `launch_gather_kernel` launched `<<<n_segs, 256>>>`, so each output port got exactly one 256-thread block regardless of its size. GPULZ split mode puts ~99% of the archive in `literals`, which meant a single block copying ~23 MB: **2.27 ms, 60.7% of the entire pipeline's GPU time, at ~20 GB/s on a 3 TB/s H100**. It hid well because `concatOutputs()` runs *after* the `DagEventTimer` bracket, so it never appeared in `dag_elapsed_ms` or in the per-stage table — only as a 2.9x host/device ratio on `gpu_zstd_lossless` (single-stream control: 1.02x), which nothing was looking at. The grid is now `(kGatherBlocksPerSegment=256, n_segs)` with all blocks in a segment's row striding through it cooperatively. **gather_kernel 2.27 ms -> 0.020 ms (112x); CLDHGH split-mode compress host wall 3.60 -> 1.33 ms, 7.2 -> 19.5 GB/s end to end**, output bit-identical. The block count is a compile-time constant rather than a function of segment size so that a captured CUDA Graph stays valid when replayed on a differently-sized input.

- **Small inputs overran the PHF encoded-blob buffer.** `d_encoded` aliases `d_scratch4`, which was sized at one `H4` word per input element — but the merged blob it has to hold is header + reverse codebook + two `pardeg` arrays + bitstream, and that is not bounded by the input length: the reverse codebook is a fixed size set by `bklen` (2,304 bytes at `bklen = 1024`) and does not shrink. Below `inlen ≈ 1,224` at that `bklen` it dominated and `memcpy_merge` wrote past the allocation, surfacing as `cudaMemcpyAsync ... invalid argument`. The boundary was exact and reproducible: 1,223 elements worked, 1,200 failed, matching `128 + revbk4_bytes + 2·pardeg·4 + (inlen/2)·4 > inlen·4` to the element. `Buf` now sizes that buffer as the max of the two requirements (`scratch4_len`); for any input large enough for the old sizing to have been sufficient it is unchanged, so there is no extra memory at scale. Test HF35 covers 1,025 / 1,100 / 1,200 / 1,500.
- **`Buf::clear_buffer()` passed element counts to `cudaMemset`, which takes BYTES.** Every buffer whose element is wider than a byte was therefore only partially cleared — `d_scratch4`, `d_bitstream4` and the three `pardeg` arrays each got a quarter of their bytes zeroed.
- **A single-symbol alphabet got a ZERO-BIT Huffman code, silently corrupting constant data.** `phf_stack::inorder_traverse` walks the tree to assign codes, but with one distinct symbol the root *is* a leaf, so it fell straight into the emit branch with `len == 0`. Nothing rejected the result: the encoder then contributed 0 bits per symbol, the partition encoded to an empty bitstream, and the decoder — which advances by the code length — could not make progress and returned zeros. Wrong data, not a failure. Affects **both** encode modes. It survived because it is nearly invisible end to end: the corrupt value is 0, and the most common constant inputs (an all-zero field, or any constant field behind a Lorenzo predictor, whose residual is 0) legitimately decode to 0 as well — so only a stage-level test with a non-zero symbol exposes it. Measured before the fix on a constant `uint16_t` stream of symbol 7: 1,279 of 3,000 symbols wrong in Coarse and in Fine. Real data reaches it — CESM-2D `SFCLDICE` and `SFCLDLIQ` are entirely zero. A one-symbol alphabet now gets the conventional 1-bit code. Test HF35.
- **The fine encode kernel read uninitialized shared memory on a trailing partial chunk, as a codebook index.** `KERNEL_CUHIP_Huffman_ReVISIT_lite` stages its chunk under `if (id < len)`, so the tail slots of `s_to_encode` are never written when `len` is not a multiple of `ChunkSize` (1024). The reduce-merge loop read them anyway and used the value to index `s_book[]`; its only guard, `(idx < allowed_len())`, suppressed the bit count and not the read. Out-of-bounds shared reads surfaced as a CUDA illegal memory access reported at the next sync point (`hf_buf.cc`), blaming an unrelated memcpy. Only reachable when the fine path actually engages, which needs every code ≤ 8 bits and so in practice a degenerate alphabet — which is exactly the case above, making the stock `cusz.toml` preset abort outright on all-zero fields. The loop now stops at the chunk's valid length, which also fixes the output: the masked version still OR-ed the out-of-range symbol's code bits into the accumulator where a later `atomicOr` could preserve them. `compute-sanitizer` memcheck/racecheck/synccheck clean. Test HF35.
- **`HuffmanEncodeMode::Fine` was unreachable on every real codebook.** `encode()` picks the fine path only when the longest code fits in 8 bits (four codes per 32-bit shard). It determined that by scanning all `rt_bklen` entries of `h_bk4` — but `phf_CPU_build_canonized_codebook_v2` memsets the book to `0xff` and leaves symbols of zero frequency at `0xffffffff`, whose bitcount field reads as **31**. Any `bklen` larger than the number of distinct symbols therefore reported 31 bits and vetoed the fine path unconditionally, so `setEncodeMode(Fine)` silently ran coarse and every fine-vs-coarse measurement was coarse-vs-coarse. The scan now skips the sentinel, which is unambiguous because real bitcounts above `FIELD_CODE = 27` are clamped to `OUTLIER_CUTOFF = 28`. On CESM-ATM this moves the reported maximum code length from a constant 31 to an actual 12–24 (`hf_hl.cc`). Test HF34.
- **`LorenzoQuantStage` silently violated its error bound on outlier overflow.** When more elements fell outside the quantizer radius than `outlier_capacity` reserved, the excess was dropped and compression reported success; the stream decoded cleanly into values off by orders of magnitude. The only signal was an `FZ_LOG(WARN)`, invisible at the default log level. It now throws a `std::runtime_error` naming the outlier percentage, the reserved capacity, and the capacity needed. `outlier_capacity = 0` remains an explicit opt-in to dropping and is unchanged. Reproduced with white noise at a tight bound: 86% of elements were outliers against 20% reserved, giving a max error of 3.8 against a bound of 1e-6; at full capacity the same data round-trips inside the bound. Test `DataPatterns/OutlierOverflowThrows`.
- **`ZigzagStage<TIn, TOut>` silently dropped the trailing partial word, emitting stale buffer contents.** `n = byte_size / sizeof(TIn)` truncates, and the kernels transform whole words only — so for any input whose length is not a multiple of the word size, the last `byte_size % sizeof(TIn)` bytes were **never written**, while `actual_output_size_` still reported the full byte count. The stage therefore emitted whatever the pooled output buffer previously held. This is reachable exactly where `byte_transparent = true` puts a 64-bit Zigzag in a lossless chain (`examples/presets/cusz_hi_cr.toml`: `RRE -> Zigzag -> RZE`), because an upstream coder's compressed length has no reason to be 8-byte aligned. The partial word is now copied through verbatim on both paths — a fragment of a word cannot be zigzagged, but it must still be written, symmetrically. Test ZS7 (poisons the output buffer, so an unwritten tail cannot pass by accident).
- Symptoms were badly misleading: the corrupt tail travelled through `RZE`, came back through the inverse chain, and garbled the `RRE` stream, which `MergeStage` then split wrongly, so `HuffmanStage`'s decode kernel walked a bogus `par_entry` out of bounds — surfacing as an illegal memory access reported at `rre_stage.cu:475`, three stages from the cause. Whether it crashed, silently produced correct output, or silently corrupted depended on what the pool buffer happened to contain. Found on EXAALT-COPPER `x.f32`, where `y.f32`/`z.f32` at identical dimensions were unaffected; the discriminator is the RRE output length mod 8, not the geometry.
- **`HuffmanStage<T>` silently emitted undecodable streams when a symbol needed a code wider than 27 bits.** `HuffmanWord<4>` holds the prefix code in a 27-bit field; when the canonical builder produced a longer code it set `bitcount = OUTLIER_CUTOFF` and `prefix_code = 0` — not a valid code — then printed one line per affected symbol to **stdout** and carried on, so the encode kernel wrote a bitstream that could not be decoded (`hf_bk.cc`). Both the reachable path (a caller-supplied frequency table, or any pre-built codebook) and the histogram path now scan the built book and throw a `std::runtime_error` naming the offending symbol; the stray stdout print is removed. Only symbols with non-zero frequency are checked, since an absent symbol legitimately gets no code. The histogram path needs a Fibonacci-like distribution over ~28+ symbols to hit this, so it is largely theoretical there — a user-supplied table reaches it trivially. `HuffmanBookSource::Adaptive` flattens its frequency floor instead of failing. Test HF30.

- **`LorenzoStage` block-mode inverse no longer ties the CTA width to the reset period.** The segmented prefix sum launched `blockDim == block_size`, so a 1024-element reset period meant 1024-thread blocks running Hillis-Steele with ~2*log2(1024) barriers — ncu flagged it as barrier-bound and decompression fell off a cliff exactly there (geometric mean 102 GB/s at `block_size = 512` down to 69 at 1024). Replaced by one CTA per segment with several elements per thread: serial scan in registers, then a warp shuffle scan, then one pass over the warp totals — 2 barriers per scan pass regardless of segment length. **CESM `Z3` decompression 86 -> 120 GB/s at `block_size = 1024`, `U` 68 -> 107**, with compression ratio and PSNR bit-identical; 1024 now matches or beats 256/512 instead of trailing them, which unlocks the highest-ratio configuration. The same kernel serves both prediction orders and centering (`passes` scans then a uniform `+ mu`), replacing three separate inverse kernels; reset periods that are not a multiple of 32 fall back to the barrier-based scan, which handles any width.

- **`LorenzoStage` 2-D/3-D inverse crashed for any dimension above 1024.** All five inverse-scan kernels (2-D row/column, 3-D x/y/z) launched one block per line with `blockDim == the scanned extent`, which exceeds the maximum CUDA block dimension — a 3600x1800 field died in `cudaGetLastError()` with `invalid configuration argument` rather than producing output. Replaced with a single `lorenzo_scan_line_kernel` shared by all five passes: one block still owns a whole line but walks it in fixed 256-element tiles with a running carry, so line length no longer depends on the block-dimension limit or on shared-memory capacity (shared memory is now sized by the block, not the extent). 7 regression tests (LZ10–LZ16) covering each axis past 1024, the exact CLDHGH geometry, and extents straddling a tile boundary; `compute-sanitizer` memcheck and racecheck clean.
- **`examples/presets/quantizer_lorenzo_bitpack.toml` had never been runnable.** It specified `nbits = 12`, which is not a power of two, so loading it threw. The pipeline was also mis-specified: `Lorenzo` emits *signed* residuals, and reinterpreting those as `uint32` puts every negative value near 2^32, so bit-packing them is a no-op no matter what `nbits` is. Inserted the missing `Zigzag` stage between `Lorenzo` and `Bitpack` and set `nbits = 16`. Now round-trips at 2.0x on CLDHGH (3600x1800) and vortex (128^3), PSNR 64.77 dB.

### Added
- **`HuffmanStage<T>` encode-path diagnostics — `getLastUsedFineEncode()` and `getLastMaxCodeLen()`.** `setEncodeMode(Fine)` is a request, not a guarantee: the fine kernel falls back to the coarse path whenever the book holds a code longer than 8 bits, and nothing observable distinguished the two, so a `Fine` pipeline could run coarse for its entire life while being benchmarked as fine. `getLastUsedFineEncode()` reports which path the last forward call actually took; `getLastMaxCodeLen()` reports the longest code in the book it used, in both modes, since that is what says whether switching to `Fine` would take effect at all. A fallback also emits one `FZ_LOG(WARN)`, re-armed only when the code length changes so a resident `Fixed`/`Adaptive` book does not warn per call. Test HF34.
- **`HuffmanEncodeMode::Fine` is now documented as experimental**, and references promoting it elsewhere (the `cusz.toml` preset, the `GPU_ZSTD_HUF_FINE` toggle in `examples/gpu_zstd.cpp`, the stage card, the execution-flow narrative) are removed — it was selected in a shipped preset while silently running coarse. `Coarse` is the only supported path. Relatedly, **CUDA Graph capture for this stage is dropped as a goal**: it would require device-side `phf_header` assembly and a device-side merge, and graph capture has not shown a measurable benefit elsewhere in the library.
- Measuring with these makes a design limit explicit: **`Fine` does not engage on realistic scientific data.** Across CESM-ATM `CLDHGH`/`CLDLOW`/`FLDSC`/`PRECT`/`TS` at `eb` `1e-2 … 1e-5` through `LorenzoQuant -> Huffman` (bklen 1024, radius 512), the longest code is 12–24 bits in all 20 cells — never ≤ 8. The barrier is structural, not a tuning matter: an 8-bit ceiling admits at most 256 codewords by Kraft's inequality, and the quantized fields carry 322–1025 distinct symbols at all but the coarsest bound. Where a ≤ 8-bit code is even constructible, package-merge puts its cost at +1.8% to +14.6% bits/symbol. **Restricting to ≤ 16 bits instead costs at most +0.31% across the same cells and is always constructible**, so a 2x16-bit shard geometry — rather than length-limiting to 8 — is the change that would make the fine path reachable.
- **`HuffmanStage<T>` pre-built codebooks (`setBookSource(HuffmanBookSource::Fixed)`).** Builds one canonical codebook up front — from a caller-supplied frequency table (`setFixedBookFromFreq`) or an analytic distribution (`setFixedBookFromModel`, with Gaussian / Laplace / GeneralizedNormal / Uniform) — and reuses it for every forward call, removing the histogram kernel, the frequency D2H, the host stream sync, and the host tree build from each compress. Following CEAZ (ICS'22) and Shah et al., *Lightweight Huffman Coding for Efficient GPU Compression* (ICS'23); the cost removed is per-call, so the benefit grows as the chunk shrinks. The reverse codebook still travels in the bitstream, so fixed-book output decodes through the stock path and the file format is unchanged. TOML keys `book_source` / `book_model` / `book_center` / `book_scale` / `book_shape` (model form only — a raw frequency table exceeds the 128-byte per-stage config slot). Model-derived books give every symbol a strictly positive frequency and so can always encode any in-range symbol; `setFixedBookFromFreq` rejects a zero bin, and both setters reject a book needing codes wider than `HuffmanWord<4>`'s 27-bit code field. Note that `Fixed` also drops the `sum(h_freq) == inlen` out-of-range symbol check, and does **not** by itself make the stage graph-capturable — `encode()` still returns the encoded size to the host. Tests HF22–HF26.
- `Fixed` costs substantially more compression ratio than a single-dataset measurement suggests, and `HuffmanBookSource::Adaptive` (below) is the better default. Over 26 (preset, field) combinations, a reasonably configured Laplace book lost a geometric mean of **-31%** (`cusz.toml`), **-83%** (`cusz_hi_cr.toml`) and **-11%** (`gpu_zstd.toml`), worst case -93%; on `cusz_hi_cr.toml` it pinned the ratio near 4.5 regardless of field, i.e. the model's entropy rather than the data set the output size. The knobs are sharp: on CESM `CLDHGH` the same book costs 3% at `1e-4` but 68% at `1e-2`. Reserve `Fixed` for when the codebook genuinely must be known before any data is seen.
- **`profiling/huffman_book_drift.cpp` (`fzgmod-profile-huffman-drift`) — measures whether a pinned Huffman codebook decays across a run.** Builds one pipeline and pushes many successive *different* steps through it (files as steps, or `--slabs N` to walk a 3-D field's levels), which is the case a single-field measurement structurally cannot show. Decompresses and error-checks every cell, flags steps with zero value range as degenerate, and reports `PerBlock` as the "refit every call" upper bound so the gap to `Adaptive` is exactly what a refit policy could recover. `--skip N` starts the fit on a later step.
- Findings (LorenzoQuant->Huffman, eb 1e-4 NOA, radius 512): `Adaptive` drift is **4.7% mean / 9.6% worst** across 23 CESM `CLOUD` levels, **8.3% / 27.6%** across 5 different CESM-ATM fields, **9.2% / 22.6%** across 20 HURR slabs — real but bounded, and well under a fixed model book's 12.6–53.2%. **But a degenerate (constant) first step poisons `Adaptive` for the whole run**: the same CESM field measures 42.0% mean when the fit lands on a constant level versus 4.7% when it does not, and constant slabs are common in real data (CESM `CLOUD` levels 0-2, HURR `CLOUDf48` slabs 18-19). `Fixed` is therefore **not** strictly dominated — it wins in exactly that case (19.5% vs 42.0%) because a generic shape degrades gracefully where an overfitted one collapses.
- **`HuffmanStage<T>` device-side symbol-range guard (`setValidateSymbolRange()`, default on).** `PerBlock` catches symbols outside `[0, bklen)` for free — the histogram kernel skips them, so `sum(h_freq) != inlen` betrays them. A pinned `Adaptive`/`Fixed` codebook skips the histogram, so that guard stopped running and the encode kernel indexed past `d_bk4`, faulting the CUDA context with no diagnostic. A grid-stride kernel now records the largest offending symbol and the stage throws before `encode()` launches. The verdict **must** be read pre-encode — a post-encode check is too late, the illegal access has already happened — so this costs one stream sync, measured at roughly 16% of `Adaptive`'s throughput at 24.7 MiB (24.4 vs 29.0 GB/s, still 1.35x over `PerBlock`) and lost in the noise at 1 MiB. It is far cheaper than the `PerBlock` path it replaces: a 4-byte device-to-host copy instead of `bklen` words, and no host tree build. Disable it for CUDA Graph capture or when the range is guaranteed upstream (`setZigzagCodes(true)` with `bklen == 2 * quant_radius`); doing so with genuinely out-of-range symbols is undefined behaviour. TOML `validate_symbol_range`. Test HF33.
- **`HuffmanStage<T>` Adaptive codebook refitting — `setRefitThreshold()`, `setRefitInterval()`, and a degeneracy guard.** Three changes that address the drift and poisoning the drift harness exposed. (1) A **degeneracy guard** refuses to pin a codebook fitted to an unrepresentative block (fewer than 2 distinct symbols, or >99.9% of the mass on one); the block is still encoded with that book, but the next call re-histograms. (2) A **bit-rate refit trigger** (`setRefitThreshold`, default 1.2) rebuilds the book once the encoded rate degrades past 1.2x the rate achieved when it was fitted — free, since `encode()` already reports `total_nbit`, so no histogram or extra kernel is needed to detect staleness. (3) An optional **periodic refit** (`setRefitInterval`, default 0 = off). TOML `book_refit_threshold`, `book_refit_interval`. `getRefitCount()` / `getFitBitsPerSymbol()` for diagnostics. Tests HF31-HF32.
- Effect on the drift measurements: stepping through 26 CESM `CLOUD` levels where the first is constant, `Adaptive` goes from **42.0% mean / 52.5% worst ratio loss to 0.86% / 3.06%** — the case that previously made `Fixed` look competitive. Across 5 different CESM-ATM variables it is unchanged at 8.3% by default, because `LHFLX`'s absolute bit rate *fell* under a mismatched book even while losing 27.6% ratio, so a rate trigger cannot see it; `--refit-interval 2` brings that to 6.9%. Deciding that case properly needs the fresh book's rate, i.e. the histogram this mode exists to avoid — so **when every call carries a genuinely different variable, `PerBlock` remains the right choice**.
- **`HuffmanStage<T>` sampled codebooks (`setBookSource(HuffmanBookSource::Adaptive)`).** Histograms the *first* forward call only, builds a codebook from that histogram, and pins it — one histogram for the lifetime of the stage instead of one per call. Frequencies are floored at `max_freq >> setAdaptiveFloorShift(k)` (default 24) before the tree is built, which guarantees a code for every symbol in `[0, bklen)` including ones the sampled block never contained (so later blocks still encode correctly) and bounds Huffman depth; the shift is halved and the build retried if the book does not fit the 27-bit code field, terminating at a uniform book. TOML `book_source = "Adaptive"`, `book_floor_shift`. Tests HF27–HF29.
- This is the mode to reach for over `Fixed`: same steady-state throughput, without the analytic model's ratio risk. Validated over 26 (preset, field) combinations — `cusz.toml` (LorenzoQuant codes, bklen 1024), `cusz_hi_cr.toml` (GInterp codes, bklen 4096) and `gpu_zstd.toml` (GPULZ literals, bklen 4096) across 5 CESM-ATM fields, 3 Hurricane-ISABEL fields and EXAALT — for a geometric-mean compression-ratio change against `PerBlock` of **-0.0% / -0.5% / -0.0%**, worst single field -1.3%, and **-0.00%** across an error-bound sweep of `1e-2 … 1e-5`. Reconstruction PSNR is identical to `PerBlock` in every cell. Throughput is provisional pending a proper benchmark machine: roughly 1.1x–1.4x geometric mean per preset on WSL2/RTX 3080 Ti (single run per cell, ~±20% run-to-run spread), 1.5x–2.2x on repeated compresses of a single field.
- Caveat on those ratio numbers: each measurement compresses one field through one pipeline, so the pinned book was fitted to exactly the data being measured. That is the optimistic bound. Ratio degradation under distribution drift across a long multi-call run is **not** measured; correctness under drift is (test HF27).
- `book_floor_shift` is far more sensitive at large `bklen`: dropping 24 -> 12 costs 1–3% ratio at `bklen = 1024` but 23% at `bklen = 4096`.
- **`AdaptiveLorenzoStage<T>` (`StageType::ADAPTIVE_LORENZO = 34`, TOML type `"AdaptiveLorenzo"`) — FSZ's prediction stage as a modular DAG stage.** Splits the input into tiles of `coder_block_size * blocks_per_tile` (default 32x8 = 256) and picks, per tile, the cheapest of four variants: LZ1, LZ2, LZ1+centering, LZ2+centering. Three properties come together here: the prediction chain runs the length of the tile rather than restarting every coder block (FSZ's cross-block prediction state, so only the tile's first one or two residuals are raw instead of one per 32 elements); selection is by **exact encoded byte cost** under `AdaptiveBitpackStage`'s rate formula, not by entropy; and all four variants are costed from a **single read**, because `delta^k(q - mu) == delta^k(q)` for every element with `k` predecessors, so the centered variants differ only in coder block 0 and their cost follows from re-rating that one block. Ports: `output` (residuals), `modes` (1 B/tile), `means` (one `T`/tile). Lossless; `int16_t` and `int32_t` instantiations.
- The cost model is exact **only for a downstream `AdaptiveBitpackStage` with `block_size = 32`**; `coder_block_size` is validated to 32 for that reason (also the only size at which each bit-plane is exactly one 32-bit word). Routing the residuals elsewhere leaves the selection reasonable but not optimal.
- **`examples/presets/fsz.toml`** — `Quantizer(linear) -> AdaptiveLorenzo -> AdaptiveBitpack(32)`.
- Side channels are compacted so they stay negligible: the mode map is packed **2 bits per tile** (4 tiles/byte), and `means` holds **only the tiles that chose centering**, indexed by an exclusive scan over the centering bits that the inverse recomputes from `modes` alone (no slot table is stored). Together 0.008 bits/element at a 256-element tile when nothing centers, against 0.156 for a dense layout. The compacted length is data-dependent, so it is resolved by a D2H in `postStreamSync()` and the stage reports `isGraphCompatible() == false`.
- Measured on 8 SDRBench fields x 3 error bounds (RTX 3080 Ti), CR against a fixed-LZ1 predictor at the same tile length — and, more tellingly, against the best *fixed* variant chosen per field (an oracle the stage has no access to):

  | tile | vs fixed LZ1 | vs per-field best fixed |
  |---|---|---|
  | 256 | 1.35x / 1.26x / 1.24x | 1.012x / 1.008x / 1.010x |
  | 512 | 1.20x / 1.14x / 1.16x | 1.008x / 1.007x / 1.008x |

  (REL 1E-2 / 1E-3 / 1E-4.) Beating the per-field oracle is the point: different tiles within one field want different variants. Up to 2.01x on CESM `T` and 1.88x on `Z3`. Sparse data no longer regresses — HURR `QRAIN` sits at 0.98-1.00x of fixed LZ1 (it was 0.73x before the side channels were compacted, an overhead exactly predicted by 32/(32/76.81 + 0.156) = 55.86 against a measured 55.88).
- Throughput cost is real and worth knowing: on CESM `Z3` at REL 1E-3, `Quantizer -> AdaptiveLorenzo -> AdaptiveBitpack` runs 66/100 GB/s (compress/decompress) against 91/106 for the fixed `Lorenzo(block_size=256)` pipeline, for 1.74x the compression ratio. The prediction kernel costs ~2.6x the fixed one (four-variant evaluation plus the compaction scan).
- **`LorenzoStage<T>::setOrder(k)` (TOML `order`) — second-order prediction (FSZ's LZ2).** `k = 2` predicts from the trend of the two preceding elements, annihilating a linear ramp where first order leaves a constant residual. Block-local LZ2 is the first difference applied twice under the same zero-padding, giving FSZ's `q_i - 2q_{i-1} + q_{i-2}`; both passes run in shared memory, so it stays one trip through global memory and needs no scratch. Requires block mode, composes with `setCentering()`, and is carried in a header byte legacy writers zeroed (so old archives read as first order).
- Measured: LZ2 alone is a **loss at loose bounds and a win at tight ones** — geometric mean 0.97x at REL 1E-2, 0.97x at 1E-3, 1.03x at 1E-4 — matching FSZ's reported 1.00x rising to 1.05x, because at loose bounds most blocks already encode to zero regardless of prediction order. At 1E-4 combined with centering it wins on 6 of 8 fields (CESM `FICE` 1.75x, `Z3` 1.52x). This is exactly the case per-tile adaptation is for; as a fixed setting it should be chosen deliberately.
- Test coverage: 16 `AdaptiveLorenzoStage` tests (`tests/stages/test_adaptive_lorenzo.cpp`, AL1-AL16) — round-trips including partial final tiles and every legal `blocks_per_tile`, header round-trip, pipeline integration, config rejection, and four behavioural assertions that the selector actually selects (centering on constant-offset data, LZ2 on a ramp, neither on sparse data, and never worse than any fixed variant), plus four on compaction (empty `means` when nothing centers, dense when everything does, strict compaction in between, and a tile count that is not a multiple of the mode-packing factor). 8 LZ2 tests and 4 segmented-scan tests (`test_lorenzo.cpp`, LZ26-LZ37).

- **Per-block mean centering on `LorenzoStage<T>` and `LorenzoQuantStage` (`setCentering(bool)`, TOML `centering`) — FSZ-style adaptive centering.** Subtracts the block's integer mean `mu` from the values before predicting. Because `delta(q - mu) == delta(q)` for every element that has a predecessor, this changes **only the first residual of each block** — the chain seed, which would otherwise be emitted as a raw value and set a downstream fixed-rate coder's bit width for the whole block. Exposed as a `"means"` output port (one `T` per block) that the inverse consumes as an extra input; reconstruction is bit-identical to the uncentered path. `LorenzoStage` requires block mode (`setBlockSize(n)`, `n > 0`); `LorenzoQuantStage` is 1-D only (the 2-D/3-D paths have no per-tile chain to seed) and uses its fixed 1024-element tile. Both must be set **at construction** — centering changes the port count and `Pipeline::addStage()` captures that at add-time — so `LorenzoStage` gains a `LorenzoStage(block_size, centering)` constructor and the TOML loader passes both as constructor arguments.
- Measured on 8 SDRBench fields x 3 error bounds (RTX 3080 Ti, `Quantizer(linear) -> Lorenzo -> AdaptiveBitpack(32)`): geometric-mean CR gain **2.01x at `block_size = 32`**, falling to 1.09x at 1024 as fewer chain restarts remain to fix. Biggest wins on constant-offset fields — CESM `T` (Kelvin) 5.27x, `Z3` 3.76x, `FICE` 3.80x at REL 1E-2. **Centering is unconditional and can lose on sparse data** where most blocks already encode to zero bytes and `mu` is pure overhead: HURR `QRAIN` drops to 0.30x at `block_size = 32`. FSZ avoids this by choosing centering per tile on measured cost; that selection is not yet implemented here, so treat the flag as opt-in per dataset.
- Both stage headers gain a `centering` byte taken from previously-zeroed `reserved` padding, so archives written before this change still decode (as centering-off) with no size or version change.
- Test coverage: 9 centering tests (`tests/stages/test_lorenzo.cpp`, LZ17-LZ25) — round-trips with a large constant offset, ragged final block, non-power-of-two block size (the mean is a block-wide reduction), header round-trip and legacy decode, port-count assertions forward and inverse, the no-block-mode rejection, reconstruction equivalence with the uncentered path, and the fused stage's 1-D round-trip plus its 2-D/3-D rejection.

- **`BitpackStage<T>` shift option — frame-of-reference base + low-bit right shift.** Forward now packs `(v - base) >> shift`; the inverse restores `(packed << shift) + base`. The two knobs compose and attack opposite ends of the word: `setBase()` removes dead high bits (values clustered away from zero — always lossless), `setShift()` removes dead low bits (**lossy unless every `(v - base)` has that many trailing zeros**). Both default to `0`, which is the previous behaviour exactly. Adaptive counterparts: `setAutoBase()` (CUB min-reduce), `setAutoShift()` (trailing-zero count of an OR-reduce of `(v - base)` — the largest shift that provably drops nothing, so always lossless), and `setAdaptive()` enabling those plus the existing `setAutoDetect()` nbits scan. On `1000 + k*16` data a `uint16_t` stream packs to 4 bits/element losslessly, a gain neither knob delivers alone. Any auto mode needs a D2H readback and so clears `isGraphCompatible()`; hand-set values stay graph-capturable. TOML keys `base`, `shift`, `auto_base`, `auto_shift`, `adaptive`.
- Bitpack serialized header grows 10 → 15 bytes (`shift` 1 B + `base` 4 B). Archives written before this option still decode, with `shift = base = 0`.
- Test coverage: 13 shift tests (`tests/stages/test_bitpack.cpp`, BP24–BP36) — manual base/shift round-trips, the documented lossy-truncation case, auto base/shift detection, the all-values-equal case where the OR-reduce is 0, a full adaptive 16→4-bit round-trip, header and save/restore-state round-trips, legacy 10-byte header decode, and an end-to-end pipeline round-trip.
- **`RLEStage<T>::setChunkSize(bytes)` — chunked run-length encoding.** Opt-in (`0`, the default, keeps the existing whole-array path and wire format). One thread block owns one chunk end to end with a block-local scan, replacing the device-wide CUB scan and the 4-kernel dependency chain with 2 kernels plus a scan over `num_chunks`. Chunked decode needs no device-to-host readback at all (element count and chunk size both ride in the serialized stage header), so unlike the whole-array path it is CUDA Graph-capturable in both directions. Sets `getRequiredInputAlignment()` to the chunk size so the pipeline zero-pads transparently; TOML `chunk_size` key. Measured on 128 MB of quantizer-like `uint16_t` codes: **encode 52 -> 136 GB/s (2.6x), decode 102 -> 177 GB/s (1.7x) at `chunk_size = 4096`, with the compression ratio unchanged at 1.50x**; 4096-8192 bytes is the sweet spot. The ratio cost is a forced run boundary per chunk plus a `4 x (num_chunks + 1)` offset table, which matters only when runs are much longer than a chunk.
- Test coverage: 7 chunked RLE tests (`tests/stages/test_rle.cpp`) — chunk-aligned and partial-tail round-trips, single element, all-same (verifies one run per chunk), alternating worst case, chunk-size header round-trip, and the word-size matrix across all 8 instantiations. `compute-sanitizer` memcheck clean.
- **`LogTransformStage<float>` — point-wise relative error bounds *with* a predictor.** Implements the transformation scheme of Liang, Di, Tao, Chen and Cappello (IEEE CLUSTER 2018): `|e|/|x| <= delta` on `x` is an absolute bound `log2(1+delta)` on `log2|x|`, so placing the log **upstream of the predictor** lets an ordinary ABS pipeline deliver the relative guarantee *and* still decorrelate. Four ports (`output`, `signs`, `outlier_vals`, `outlier_idxs`); sign bitmap packed one-thread-per-output-byte (no atomics); zeros/denormals/inf/NaN and sub-`threshold` values stored losslessly; outlier count carried in stage-private device scratch → `postStreamSync()` → FZM header, mirroring `QuantizerStage`. Graph-capture compatible. `StageType::LOG_TRANSFORM = 33`, TOML type `"LogTransform"`.
  - Measured on `CLDHGH.f32` @ delta=1e-3: **ratio 6.36 vs 1.00 for `QuantizerStage` REL — 6.4x the compression at an identical guarantee and identical PSNR (80.99)**, zero bound violations across 6.48 M elements.
  - `quantizerErrorBound()` returns `log2(1+delta) - kLogRoundTripSlack`, reserving slack for the transform's own float32 `exp2(log2(x))` rounding; without it a handful of elements land marginally over the composed bound. The forward pass additionally verifies each element's actual round-trip and escalates anything worse than budgeted to a lossless outlier. `minimumErrorBound()` (~1.4e-6) is the float32 floor, below which `execute()` throws rather than emit a stream that violates its bound.
  - **The downstream quantizer's `eb` is the caller's job** — a stage cannot configure another stage across the DAG. Passing the raw `delta` instead is a ~693x looser bound with no error and no warning; see `docs/stages/log_transform.md`.
  - 14 tests (`tests/stages/test_log_transform.cpp`), including an end-to-end DAG round-trip and a bound-holds check across six decades of magnitude.
- **`ErrorBoundMode::PREL` — the honestly-named pseudo-relative mode.** `abs_eb = eb × max(|data|)` applied as a single absolute bound. This is what `LorenzoQuantStage` and `GInterpStage` have always done under the name `REL`; giving it its own name makes the distinction from an actual per-element guarantee impossible to miss. `REL` now means exclusively "guaranteed `|e|/|x| <= eb` for every element", which only `QuantizerStage` implements (log-space quantization). `QuantizerStage` also accepts `PREL` for uniformity. TOML `"PREL"` and CLI `--mode prel` added.
- **`examples/eb_mode_analysis.cpp`** — measures what each error-bound mode actually delivers on your data: resolved absolute bound, ratio, PSNR, and a *pointwise relative error profile bucketed by element magnitude*. On `CLDHGH.f32` @ eb=1e-3 the PREL row degrades ~10× per decade below peak magnitude (9.9× / 90.9× / 333.3× the requested bound, 74% of elements in violation) while `QuantizerStage` REL stays at 1.0× with zero violations. Also shows REL's compression ratio of 1.00 — exact but uncompressed, because it quantizes raw values with no predictor in front.

### Changed
- **Huffman coarse-path `sublen` is now size-adaptive instead of the constant 768.** `capi_phf_coarse_tune_sublen()` took `inlen` and ignored it, pinning `pardeg = ceil(n/768)` — the coarse path's entire parallel decomposition — at a value tuned for cuSZ v1.x. It now targets `pardeg ~= 131072`, floored at the historical 768 so nothing below ~100M elements changes and no configuration can regress. Validated on H100 over 67 matched cells against a held-out field set: **compress 1.15x, decompress 1.08x, ratio 1.008x geomean overall**, rising with input size — HACC 281M elements **1.96x compress / 1.47x decompress**, CESM-ATM 168M **1.31x / 1.10x**, NYX 134M **1.14x / 1.10x**, everything below 25M unchanged. Compression ratio never regressed on any cell (min 1.000x) and PSNR is unchanged in all 67. `sublen` travels in `phf_header`, so this is not a format change and existing archives decode with their own geometry. `FZ_HF_SUBLEN` overrides it, which is also how to take the smaller-sublen throughput/ratio trade that pays off below ~26 MB (sublen 256: +27% compress, +161% decompress, -3.9% ratio).
- **`AdaptiveLorenzoStage` forward rewritten to be warp-cooperative** (`adaptive_lorenzo_forward_kernel`). Two barrier-bound sections went at once. The tile mean ran a shared-memory tree reduction (`log2(tile_size)` barriers, 8 at the default 256-element tile) and is now a warp shuffle reduction over per-warp partials; the first/second differences staged the whole tile into shared memory twice (4 more barriers) and are now `shflUp` neighbour reads, with only the last two values of each warp published so lane 0 can reach across the warp boundary for both `d1` and `d2`. **16 barriers -> 2** at a 256-element tile, and the kernel now needs no dynamic shared memory at all (per-warp state is <= 32 entries). Centering was paying for barriers rather than arithmetic: on NYX 512³ its cost over the uncentered path fell **0.771 -> 0.279 ms (2.8x)**, taking the whole stage **1.725 -> 1.257 ms (1.37x)** and **2.002 -> 1.397 ms (1.43x)** at `blocks_per_tile = 16`. End-to-end FSZ compress **1.11-1.21x** across CESM/HURR/NYX/HACC. Output is **bit-identical** — verified by comparing compressed payloads (below `header_size`, since the FZM header itself is not byte-reproducible) across 10 cases: four preset variants, a 3-D field, and five synthetic sizes from one tile to 256 tiles. `compute-sanitizer` memcheck/racecheck/synccheck clean, suite 48/48. The one cost: with `enable_centering = false` there is no mean to reduce, so publishing the per-warp boundary values does not pay for itself and that ablation arm is ~1% slower (0.989-0.996x, consistent across all four fields).
- **`AdaptiveLorenzoStage` inverse rewritten as a two-level warp scan** (`adaptive_lorenzo_inverse_kernel`). It ran a shared-memory Hillis-Steele scan with two `__syncthreads()` per stride — `2*log2(tile_size)` barriers per pass and twice that for order-2 tiles, 32 barriers at the default 256-element tile — making it barrier-bound rather than memory-bound, the same failure mode already fixed in `TiledLorenzoStage` and the 1-D `LorenzoStage` scan. The warp-level scan needs no barriers, so a pass costs 2 regardless of tile size, and shared memory drops from `tile_size` elements to at most 32 warp totals. **AdaptiveLorenzo inverse 0.814 -> 0.615 ms on NYX 512³ (1.32x); FSZ end-to-end decompress 1.07-1.20x** across CESM/HURR/NYX/HACC, largest at `blocks_per_tile = 16` where the old barrier count was highest. Output is **bit-identical** (verified by git-stash A/B on four preset variants plus a 3-D field); `compute-sanitizer` memcheck, racecheck and synccheck all clean.
- **`ErrorBoundMode::REL` is deprecated on `LorenzoQuantStage` and `GInterpStage`.** Both now route it through `resolveApproxRelMode()`, which maps it to `PREL` and emits a `WARN` — at the setter and again at execute time, so a mode supplied via the `Config` struct is caught too. Existing code keeps working; it just says out loud that it is not getting a per-element guarantee. Headers written before the split (`eb_mode == REL`) deserialize as `PREL` silently, since decode uses the stored absolute bound regardless. The CLI's `--mode` default (`rel`) maps to `PREL` on predictor stages without warning — only an explicit `--mode rel` warns.
- `examples/presets/gpu_zstd.toml`, `examples/{ownership_example,debug_logging,file_io_example,compare_predictors,gpu_zstd}.cpp` and the GInterp tests updated from `REL` to `PREL`. `examples/presets/speed.toml` keeps `REL` — it is a `Quantizer` stage, where REL is the exact mode.
- **`scripts/new_stage.sh` scaffolds backend-neutral includes** — the generated `_stage.h`/`_stage.cu` now use `backend/types.h` / `backend/api.h` instead of `<cuda_runtime.h>`, so a new stage starts HIP-clean rather than needing a retrofit. The full set of required substitutions is documented in a new Step 3b of `docs/how_to_add_a_stage.md` (and `memory/hip_compliance.md`).
- **`GPULZStage` split-mode inverse decodes straight from the four ports** (`gpulzSplitDecodeKernel`), replacing the restripe-then-decode pair. Reading the ports directly also drops the shared-memory staging of the packed byte stream.

### Fixed
- **`LorenzoQuantStage` and `GInterpStage` under-allocated their inverse output buffer.** Both had a direction-blind `estimateOutputSizes()` that always derived the element count as `input_sizes[0] / sizeof(TInput)`. On the inverse path `input_sizes[0]` is the *codes* buffer, so the count came out `sizeof(TInput)/sizeof(TCode)` too small (2x for the usual float/uint16 pair) and the inverse kernel's opening `cudaMemsetAsync` ran past the end of the buffer. Latent for the entire life of both stages because each was always the pipeline's *source*, and `buildInverseDAG()` overrides a source's result buffer with the exact known uncompressed size — it only bites when a stage sits upstream of them, which `LogTransformStage` is the first to do. Exactly the failure mode `docs/how_to_add_a_stage.md` warns about under "Non-size-preserving stages: bidirectional estimateOutputSizes".
- **FZM file buffers are now 16-byte aligned, matching the in-memory concat path.** `buildHeader()`/`writeToFile()` packed buffers back-to-back, so a buffer whose size was not a multiple of 4 left the *next* one on an odd offset — and the Huffman and ANS decode kernels read their bitstreams as 32-bit words and fault on the misaligned load. Latent for any multi-buffer archive; surfaced by the GPU-Zstd preset's six leaf outputs (in-memory `decompress()` was unaffected, since `ConcatLayout` already padded slots to 16). Reading is backward compatible — every buffer is located through `entry.byte_offset`, so older unpadded files still open — and the blob is pre-zeroed so the padding is deterministic.
- **`HuffmanStage::setBklen()` now rounds an odd `bklen` up to even.** The reverse codebook is `4*(2*32) + sizeof(SYM)*bklen` bytes, so with a 2-byte symbol an odd `bklen` made it an odd number of 16-bit words, shifting the bitstream section to a 2-mod-4 offset — and `KERNEL_CUHIP_HF_decode` reads the bitstream as `uint32*`, faulting on the misaligned load. Latent for any caller passing an odd `bklen`; surfaced by the GPU-Zstd pipeline using `2*radius - 1`.
- **`GPULZStage` no longer requires chunk-aligned input**; `getRequiredInputAlignment()` returns 1 and the stage zero-pads its own tail chunk. Pipeline-level alignment cannot work for a coder behind a width-changing stage: `finalize()` pads the *pipeline input*, but `LorenzoQuantStage` halves bytes per element, so the coder sees an unaligned size anyway — and forcing the input up grows the upstream stage's output past its own estimate and trips the buffer-overwrite check.
- **`GPULZStage` split ports report 4-byte-aligned sizes** (rounded up, pad zero-filled), matching the convention `RREStage` already follows. Archive slots and downstream buffers assume it; a port ending on an odd byte pushes the next buffer off alignment and faults the Huffman/ANS decode kernels, which read their bitstreams as 32-bit words.

- **Per-stage source fingerprints: `fz::stageFingerprints()`, `stage_versions` in `--report-json`, and fingerprints in `--list-stages`** — each registered stage now carries a sha256 (truncated to 16 hex chars) over its own sources **plus the transitive closure of its repo-local `#include`s**, generated at build time by `scripts/gen_stage_fingerprints.py` from the `source_dir` field added to `kStageRegistry`. The transitive part is what makes it correct rather than decorative: stages share infrastructure (`backend/api.h` is included by 33 files, `stage/stage.h` by 25) and include *each other* (`transforms/zigzag/zigzag.h` by 6 stages, `fused/lorenzo_quant/lorenzo_quant.h` by 5), so a per-directory hash would miss a memory-pool change entirely. Verified: editing `adaptive_bitpack_kernels.cu` moves exactly 1 fingerprint, editing `transforms/zigzag/zigzag.h` moves 4 (Zigzag plus the three stages that inline it), and editing `include/mem/mempool.h` moves all 25. Exists so a consumer caching expensive results per stage can tell whether the code behind a stored number has changed — something a pipeline-config hash cannot answer, since editing a `.cu` file changes no config. Deliberately conservative (comment-only edits move it: proving an edit semantically inert is not something a hash can do, and a needless re-run is far cheaper than a wrong cached result) and deliberately automatic (no version integer for anyone to forget to bump). The generator fails the build if a registry entry names a nonexistent directory or lacks a `source_dir`, and rewrites its header only when a fingerprint actually changes so it does not retrigger compilation. `--list-stages=json` moves to schema 1.1 (adds `fingerprint`); `stage_versions` is omitted entirely when unavailable, so a consumer can distinguish "this build does not report versions" from "nothing changed".
- **`fz::registeredStageTypes()` (`include/pipeline/config.h`) and `fzgmod-cli --list-stages[=json]`** — expose every stage `type` string a TOML config accepts. Both derive from the same `kStageRegistry` that drives load/save dispatch, so adding a stage per the documented procedure updates them automatically. Motivated by a consumer that needs the stage *inventory* rather than an execution trace: a downstream benchmark harness invalidating cached results per stage must know a stage exists even when no current pipeline uses it, and names scraped from report JSON only ever cover what happened to run. The prose stage list in `config.h`'s file comment had already drifted — it omitted GInterp, AdaptiveBitpack, TiledLorenzo, GPULZ, ANS, Huffman and ADM — and now points at the accessor instead of restating the set.
- **`GPULZStage::setMatchLevel()`** — encode-side match-search effort, 0 or 1 (default 1). Level 0 searches only the exact 32-element near window; level 1 additionally consults a shared-memory hash table for long-range candidates (offsets up to 255, the limit of the token's one-byte offset field). Motivated by measurement: compression ratio was still climbing steeply with window size (4.36x at window 32, 4.82x at 48, 5.13x at 64) while the exhaustive search costs one comparison per element per offset, so it cannot be widened far — a hash lookup finds a candidate in O(1) regardless of distance. The chunk is walked in 8 sub-blocks and the table only ever holds positions from earlier sub-blocks, so a hit is always a legal back-reference needing no ordering fixup. Two details carried most of the benefit: the key covers **two** consecutive words rather than one (on quantized data most single values are small integers that recur constantly, so a one-word table just rediscovers a nearby duplicate the near window already covers — ratio 4.70x → 5.01x at identical throughput), and positions where the near window already found a long match skip the lookup entirely (throughput 117 → 130 GB/s at unchanged ratio). Buckets are filled with `atomicMax` on position+1 rather than a plain store, so the bucket winner — and therefore the compressed bytes — does not depend on thread scheduling. The level is **not** part of the stream format and is not serialized: a stream produced at either level decodes identically. Measured on an H100 over 24.7 MB of Lorenzo-quantized `CLDHGH` residuals at `chunk_size=2048, word_size=4`: level 0 gives 124 GB/s at 4.36x, level 1 gives 109 GB/s at 5.08x; at `chunk_size=4096, word_size=4`, level 1 reaches 5.30x.
- **`fz::backend::atomicMaxBlock`** (`include/backend/atomics.h`) — block-scoped atomic max, alongside the existing `atomicAddBlock`/`atomicOrBlock` facades (`atomicMax_block` on CUDA, `__hip_atomic_fetch_max` with workgroup scope on HIP).
- Test coverage: 6 new `test_gpulz.cpp` cases — round-trip at both match levels across all word sizes and chunk sizes, a stride-40 stream whose only redundancy lies outside the near window (asserting level 1 compresses it strictly better than level 0), cross-level decode (a level-1 stream decoding on a stage never told the level), and repeated-compression byte-for-byte determinism. `compute-sanitizer --tool memcheck` and `--tool racecheck` both clean.

### Changed
- **`GPULZStage` decode kernel rewritten from one thread per chunk to one CUDA block per chunk** — upstream GPULZ's `decompressKernel` replays a chunk's item stream sequentially on a single thread, which is what made decode the stage's slowest path. The serial dependency is only apparent: the flag bitmap alone fixes every item's *input* size (2 bytes per match token, `word_size` per literal), so a block scan recovers all input offsets at once; reading each match's length byte then gives every item's output length, and a second block scan recovers all output positions. The one genuinely sequential structure — back-references chaining onto other back-references — is resolved by pointer doubling over a per-element source-index array (`log2(chunk elements)` parallel rounds, with early exit) instead of by replaying the stream in order. Measured on an H100 over 24.7 MB of Lorenzo-quantized `CLDHGH` residuals: decode 50.0 → 121.9 GB/s at `chunk_size=2048, word_size=4`, and 32.3 → 130.7 GB/s at `chunk_size=4096, word_size=4`. Threads-per-block tuning on the old kernel was measured first and did nothing (46–51 GB/s across 32/64/128/256), confirming the rewrite rather than a launch-config change was needed.
- **`GPULZStage` encode kernel: exact longest-match search, `cub::BlockScan`, and staged coalesced writes** — phase ablation attributed 68% of encode time to the sliding-window match search, 20% to the sequential parse, and 11% to everything else, so the search was replaced. Upstream advances its window pointer on every step, so a match it finds consumes the candidate offsets behind it — a greedy approximation that systematically settles for a shorter match than exists. The new search builds an offset-indexed equality mask (bit `o-1` of `omask[i]` set iff `buffer[i] == buffer[i-o]`) and AND-s successive masks, so each AND drops exactly the offsets that just stopped matching and the extension loop runs `longest_match + 1` times for *all* offsets at once rather than once per candidate offset. Being exact, it also compresses better, and matches may now exceed the 32-element window (capped at `GPULZ_MAX_MATCH` = 255, the token's length-field limit). The Blelloch scan was replaced by `cub::BlockScan` and the per-byte scatter to global scratch by emission into a shared staging buffer followed by coalesced 32-bit stores. Same stream format. Measured on an H100 at `chunk_size=2048, word_size=4`: encode 64.3 → 125.3 GB/s **and** compression ratio 3.99x → 4.36x; at `chunk_size=4096, word_size=4`, 64.1 → 114.7 GB/s and 4.10x → 4.48x. The sequential literal/match parse is unchanged and is now the largest single cost in the kernel (~47%).

### Fixed
- **Two real bugs found porting RARE/RAZE, both in the new partial-keep bit-pack path (no precedent in RRE/RZE, which only ever emit whole words):** (1) the trailing `atomicOrBlock` write ran unconditionally per thread, including "empty" threads whose whole `ept`-range lies past the chunk's element count (unavoidable whenever `ept*TPB` overshoots `size`, e.g. `size=2048/ept=8/TPB=512` leaves 256 empty trailing threads) — such a thread's `wloc2`/`wpos2` retain a stale pre-loop value that grows unboundedly with `keep`, driving an out-of-bounds shared-memory write (silent corruption for narrow words, a genuine `compute-sanitizer`-caught fault for `word_size=8`). ### Changed
- **`LorenzoStage` 1-D block-local inverse (`block_size=32`, the cuSZp2/cuszp2 path) gained a barrier-free warp-scan fast path (`lorenzo_scan_1d_warp32_kernel`).** The existing `lorenzo_scan_1d_kernel` did a shared-memory Hillis-Steele inclusive scan (5 log-steps × 2 `__syncthreads` = 10 barriers) launched with 32-thread blocks — one warp per 32-element reset segment, but capped at ~50% occupancy on the blocks-per-SM limit and paying block barriers for what is a pure intra-warp scan. ### Fixed
- **Latent cub-scratch-buffer ownership bug at several call sites (`RLEStage`, `AdaptiveBitpackStage`)**: temp-storage cleanup decided whether to route a pointer to `pool->free()` vs. a raw `cudaFree()` by checking `pool != nullptr` at free time, rather than tracking whether the pointer actually came from the pool. If `pool` was non-null but `pool->allocate()` itself returned `nullptr` (e.g. pool exhaustion) and the site fell back to a raw `cudaMalloc()`, the old check would still route that raw pointer to `pool->free()` — undefined behavior. `AdaptiveBitpackStage`'s two cub call sites additionally had no fallback at all (`pool->allocate()`'s result was passed straight to `cub::DeviceScan::ExclusiveSum` unchecked), so pool exhaustion there meant calling cub with a null scratch pointer and a nonzero required size. Surfaced while unifying these call sites onto the new `fz::backend::withTempStorage()`/`freeTempStorage()` facade (see Added), which tracks allocation provenance explicitly (`TempStorage::from_pool`) instead of re-deriving it. Exercised only under pool exhaustion, which none of the existing tests trigger by design (the fallback path exists for the vGPU/testing `force_fallback` case, and *that* path was always pool-absent, not pool-present-but-exhausted) — so this had no observed failure, but is a real fix, not a refactor. All affected stage tests still pass under `compute-sanitizer --tool memcheck`.
- **`RLEStage<T>`'s packed wire format hardcoded a 4-byte-aligned values section** (`[num_runs:u32][values:T×n][lengths:u32×n]`, values starting immediately at byte offset 4). For 8-byte `T` (`uint64_t`/`int64_t`, added in this release) that reinterpret-casts a `T*` onto a 4-byte-aligned address, which faulted with "unspecified launch failure" on both the forward pack kernel and the inverse decode read the moment those word sizes were exercised. Fixed by introducing `rleValuesOffset<T>()` (rounds the values-section start up to `alignof(T)`: 4 bytes for T ≤ 4 bytes, 8 bytes for 8-byte T) and using it consistently in `estimateOutputSizes()`, `completePendingSync()`, `rle_pack_kernel`, and the inverse `execute()`; the new header-to-values gap is explicitly zeroed. All 8 word sizes now round-trip clean under `compute-sanitizer --tool memcheck`.
- **`d_REencodebyteshort`/`d_ZEencodebyteshort` (the `word_size ∈ {1,2}` fast path in `lc_chunk_components.cuh`, shared by `RZEStage`/`RREStage`) wrote their per-thread bitmap contribution at a stride hardcoded for the original `CS=16384, TPB=512` configuration** (`bmout[tid*4+0..3]` for byte words, `bmout[tid]` for short words) — for any other chunk size the meaningful bitmap bytes per thread (`bytesperthread/(8*sizeof(type))`) no longer matched that hardcoded stride, silently producing a gapped bitmap that the (already chunk-size-agnostic) decoder reads as tightly packed, corrupting the reconstruction. Surfaced while adding `chunk_size` configurability below (`RZEStage.ChunkSize8192PartialChunkRoundTrip` with low-entropy input). Fixed by writing a generically tightly-packed bitmap (loop over the actual per-thread byte count) and tightening the dispatcher guard so the fast path is only selected when `wordsperthread >= 8` (at least one full bitmap byte per thread), otherwise falling through to the already-correct general-purpose dispatch. `chunk_size=4096` combined with `word_size=2` is the degenerate case (< 1 bitmap byte per thread) that now correctly falls back instead of silently miscompressing. New tests `RZ22`/`RR22` (`ChunkSize4096WordSize2RoundTrip`) cover the fallback path; `compute-sanitizer --tool memcheck` and `--tool racecheck` both clean.
- **Non-deterministic compression (multi-output pipelines) + the `-b`/streaming decode buffer-overflow crash (E19).** Repeated compression of identical input produced different blobs, and a reused MINIMAL decode pipeline could write past its output buffer (`rzeDecodeKernel` OOB). Every *stage* output was deterministic; the non-determinism was in the DAG assembly, from four independent sources, all fixed:
  1. `Pipeline::autoDetectUnconnectedOutputs()` iterated `stage_to_node_`, a `std::unordered_map` keyed by `Stage*` pointers, whose order depends on heap addresses (ASLR). That order fixed the concat layout of multi-leaf pipelines (e.g. both cuSZ-Hi presets: codes chain + outlier chain), so segments were permuted run-to-run — same size, ~93% of bytes "different", decoding correctly. Single-output pipelines were immune. Now iterates `dag_->getNodes()` (deterministic insertion order).
  2. `GInterpStage::serializeHeader()` built `GInterpConfig` on the stack without zeroing, emitting uninitialized alignment padding into the serialized header (a few garbage bytes). Now `memset`s the struct first.
  3. `GInterpStage` outlier compaction scatters via `atomicAdd`, so the order of `outlier_vals`/`outlier_idxs` was non-deterministic (which thread claims which slot). Order doesn't affect correctness (the inverse scatters back by index) but changes how the downstream `Merge→Bitshuffle→RRE→RZE` chain compresses those arrays, so the blob **size** varied run-to-run — which undersized the reused inverse RZE output buffer (sized from a prior run's `cached_orig_bytes_`) and caused the E19 OOB. Now sorts `(idx, val)` by index after the forward kernel (`cub::DeviceRadixSort::SortPairs`); counts are ~0.001–0.004 % of N so the sort is negligible. Skipped under CUDA-graph capture (can't read the host count; capture only runs under PREALLOCATE, which sizes buffers to worst case once, so the size-variation crash can't occur there).
  4. Defensive: the GInterp codes buffer is sized to the padded element count `N` but the spline writes only the logical `dims` grid, and `Pipeline::concatOutputs()` pads each segment slot to 16 B (`ConcatLayout::slotSize`) — both left stale bytes the codes chain / final blob compressed. Now zero the codes buffer over `N` before the kernel and the concat buffer before the gather.
  Result: `cusz_hi_tp` and `cusz_hi_cr` are now bit-reproducible across runs, and `compute-sanitizer --tool memcheck` on `-b --runs 6` reports 0 errors (was a deterministic OOB). Round-trip fidelity/CR unchanged (CLDHGH 66.83 dB, 12.46×). New test `tests/pipeline/test_lc_presets.cpp` `LCPresets.DeterministicCompress` (outlier-heavy input, asserts 3 repeated compresses are byte-identical). Full suite green (ginterp 54, lc_presets 4, memory_strategies 21, concurrency 6, rre/rze 15/15).
- `GInterpStage` / `LorenzoQuantStage` NOA/REL value-range scan included the input buffer's zero-padding tail, over-loosening the error bound on all-positive fields. `Pipeline::computeInputAlignment()` rounds the input buffer up to the LC chunk alignment (16384 B) and zero-pads the tail; the `computeValueBase()` min/max scan used the padded element count (`input_bytes / sizeof`), so a padding zero became the array minimum. For NOA (`abs_eb = eb·(max−min)`) on a strictly-positive field this collapsed the bound to `eb·max` — over-loosening it by `min/range` (e.g. CLDHGH ≈ 0.19%, NYX ≈ 0.05%), so the realized max error exceeded the intended bound by that ratio (the cross-tool "eb overshoot" of 1.00187 seen on CESM/CLDHGH). Fields straddling zero were unaffected (a padding zero sits inside their real range). Fix: scan only the logical grid (`dims` product), guarded to fall back to the full length when dims are unset. Overshoot drops to the float32 quantize/reconstruct floor (~1.00003, a handful of elements) — the same residual native cuSZ/fzgpu exhibit. Round-trip fidelity unchanged (CLDHGH 66.81→66.83 dB); CR unchanged (12.47→12.46×). Applied to all three predictors: `GInterpStage`, `LorenzoQuantStage`, and `QuantizerStage`. `QuantizerStage` had no `dims` member (flat stage), so a runtime-only `dims_` hint + `setDims()` override were added (not serialized — decode never scans); verified directly on a `Quantizer(NOA)→Bitshuffle→RZE` pipeline over all-positive CLDHGH, overshoot 1.00187 (11,666 violations) → 1.00007 (float floor). It didn't surface in pfpl only because its Difference predictor keeps residuals ≈0.1× the bound.

- `modules/fused/ginterp/ginterp_stage.cu` — the forward pass left the **tail of the `outlier_vals`/`outlier_idxs` ports uninitialized**. The scatter kernel fills only slots `[0, outlier_count)`; the rest of the worst-case capacity was whatever the recycled pool page held. `postStreamSync()` trims the reported sizes to the actual count, but that runs only *after* the whole pipeline completes, so mid-pipeline consumers (`MergeStage`) read these ports at full capacity **including the stale tail** during the DAG run. ### Changed
- **`RZEStage`/`RREStage` `chunk_size` is now configurable (`4096`, `8192`, or `16384`; default unchanged at `16384`)**, was hardcoded to throw for anything but `16384`. - **All remaining device-wide barriers in stage execute/postStreamSync paths removed.** Extended the stream-scoped D2H/H2D conversion to every remaining plain `cudaMemcpy` call that ran on the legacy default stream (a device-wide barrier). Inverse execute path: `BitplaneRZEStage` ArchiveHeader read (`:59`). Forward execute paths: `HuffmanStage` histogram readback (`:147`), `predictor_utils.cuh` pmin/pmax readback (`:96/:98`; now async + single stream-scoped sync, replacing an earlier explicit sync + two device-wide copies), `BitplaneRZEStage` encode offset_counter D2H + archive-header H2D (`:144/:159`). `postStreamSync` overrides in all six remaining stages (`LorenzoQuantStage`, `QuantizerStage`, `GInterpStage`, `RZEStage`, `RREStage`, `AdaptiveBitpackStage`) — each now passes `stream` to the override (base class already declared `cudaStream_t stream`), issues `cudaMemcpyAsync` on the caller's stream, and follows with a stream-scoped `cudaStreamSynchronize`. `RZEStage`/`RREStage` `getActualOutputSizesByName()` (the user-callable const path) converted identically. Alignment-padding `cudaMemset` in `RZEStage`/`RREStage` `postStreamSync` also converted to `cudaMemsetAsync` + stream-scoped sync. The net effect: all CUDA D2H/H2D host↔device communications in FZGPUModules stage code now use explicit-stream async copies; no stage issues a plain `cudaMemcpy` (blocking on the default stream) during a pipeline execute or postStreamSync. Debug-only assertions inside `#ifndef NDEBUG` blocks in the ADM transforms are the sole remaining use of plain `cudaMemcpy` and are compiled out in release. `profiling/decompress_concurrency.cu` extended with a `bitplane_rze` pipeline option to exercise the newly-unblocked inverse path.
- **Inverse coder header reads made stream-scoped (was device-wide).** `HuffmanStage` (`:197`), `RZEStage` (`:376/:385`) and `RREStage` (`:375/:384`) read their in-stream header on the **inverse/decode** path with a plain `cudaMemcpy` — which runs on the legacy default stream and is a device-wide barrier (the build does not use per-thread default stream), so decode calls on different streams/instances could not overlap. Switched to `cudaMemcpyAsync(..., stream)` + `cudaStreamSynchronize(stream)` (matching the pattern `RLEStage` already used): the sync now stalls only the calling thread, so K-threaded decode loops overlap on the GPU. The host still blocks to read the header before launching the dependent decode kernels (unavoidable with these wire formats), but it is no longer a device-wide stall — important for running a decompressor concurrently with other GPU work (e.g. a scientific simulator). `AdaptiveBitpackStage`'s only plain `cudaMemcpy` is forward-only (`postStreamSync`, guarded `if (is_inverse_) return`), so its inverse path was already clean; PHF decode internals use only stream-scoped syncs. Validated with the new `decompress_concurrency` probe: cuSZ (Huffman) 2.98×, PFPL (RZE) 2.36×, RLE 2.56× at 4 slots (was ~1.0× device-serialized). Forward-path readbacks (outlier counts, compressed sizes) are unchanged — they only affect concurrent *compress*, which is a separate follow-up. Pinning the RZE/RRE H2D offset tables (a thread-local latency polish, not a barrier) is deferred.
- **Decompress path de-serialized for cross-stream concurrency.** The caller-owned-buffer `decompress()` overload no longer routes through a temporary `cudaMalloc`'d buffer + D2D copy + `cudaFree` + a second `cudaStreamSynchronize`; it now injects the caller buffer directly as the inverse DAG result pointer (removing two device-wide allocator barriers and a redundant copy/sync that blocked decode calls on different streams from overlapping). All three decompress overloads (`void**`, caller-buffer, and the new `decompressInto`) now share one parameterized `decompressCore()` (caller-output / synchronize knobs); the pool-owned and `void**` behaviour is unchanged. Diagnosed on BigRed200 (`memory/fzgm_decompress_overlap_fix.md`): 3 instances decompressing on 3 streams previously ran at 1.0× serial speed.
- `BitplaneRLEStage` renamed to `BitplaneRZEStage` (`modules/fused/bitplane_rze/`); `StageType::BITPLANE_RZE` (numeric value 23 unchanged, FZM binary backward-compatible). TOML config type string changed from `"BitplaneRLE"` to `"BitplaneRZE"` (breaking for existing TOML pipeline configs). Namespace: `fz::bitplane_rze`.
- `AdaptiveBitpackStage<T>` forward (compress) path is now **graph-compatible** (`isGraphCompatible()` returns `!is_inverse_`, was unconditional `false`). cuSZp's data-dependent compressed-size readback (`cmpSize` D2H + the `cudaStreamSynchronize` it required) was moved out of `execute()` into a new `postStreamSync()` override, which the pipeline calls after the launch and a full stream sync — outside any CUDA-graph capture window. To support reading the scanned payload length post-sync (and to avoid any allocation inside a captured graph replay), the per-block cost/offset arrays are now **persistent** pool scratch (`allocate(..., persistent=true)`, grown lazily when a larger input is seen, freed in the destructor) instead of per-execute alloc/free; the CUB scan temp stays transient. `execute()` sets a worst-case provisional `actual_output_size_` (graph *recording* does not invoke `postStreamSync`), which `postStreamSync()` then refines to `meta_region + scanned_payload`. - `AdaptiveBitpackStage<T>` (`modules/coders/adaptive_bitpack/`, `StageType::ADAPTIVE_BITPACK = 24`) — a per-block adaptive fixed-rate bit-plane coder: the cuSZp lossless back-end's "plain" mode as a modular stage. - `BitplaneRLEStage` (`modules/fused/bitplane_rle/`, `StageType::BITPLANE_RLE = 23`) — the FZ-GPU lossless encoder, ported as a fused single-kernel stage.
