# FZGPUModules 2.0.0 release notes — draft

This draft describes the changes since the historical `release` tag (1.0).
The release is pending review; the changelog remains under `Unreleased`.

## API and migration

- The configuration-driven `fz::Config<T>` / `fz::Compressor<T>` API in
  `fzmod.hh` has been replaced by `fz::Pipeline` in `fzgpumodules.h`. Applications
  assemble stages, connect named ports, finalize the graph, and execute it.
  Rebuild and migrate existing consumers using the
  [quick start](../../README.md#quick-start) and [API reference](../api_reference.md).
- Device spans and explicit borrowed/owned buffer types distinguish pipeline
  memory from caller-owned allocations. Pointer overloads remain available in
  the current API. Pipeline-owned outputs must not be freed by the caller.
- TOML graph configuration and the CLI provide stage composition, preset
  workflows, archive I/O, and execution reports. The stage catalog now includes
  additional predictors, quantizers, transforms, coders, and structural stages.
- Pipeline Specialization recognizes eligible graph regions and installs
  registered implementations for compression and decompression. `Off` remains
  the default; `Auto` uses admitted implementations. `Force` remains available,
  but all shipped implementations are already admitted for `Auto`. `Auto` does not currently
  predict whether specialization will be faster for a particular input.
- The current specialization API uses `SpecializationPolicy`,
  `setSpecializationPolicy()`, and `FZ_SPECIALIZE`. Earlier development names
  (`FusionPolicy`, `setFusionPolicy()`, and `FZ_FUSION`) remain compatibility
  aliases. These aliases do not restore the historical 1.0 API.

The major version changes the shared-library ABI. Recompile applications and
external stages against the installed headers; do not mix 1.0 headers or binaries
with the 2.0 libraries. The shared-library major version is 2.

## Supported execution

Stable main supports CUDA only. HIP/ROCm backend development is preserved on
`development`; HIP and SYCL configurations are unavailable in the stable build.
Specialization supports a bounded set of registered shapes and numeric modes;
unsupported graphs continue with staged execution.

CUDA JIT specialization supports independent pipelines sharing one CUDA primary
context on one device per process, including concurrent first use. The cache
retains that primary context until process exit. Custom contexts and changing
contexts or devices are rejected at lookup; resetting the owning context with
`cudaDeviceReset()` is unsupported. Concurrent execution requires separate
pipeline instances and their own mutable state.

Specialization and CUDA Graph capture are mutually exclusive. Warm up generated
kernels before timing steady-state execution; first use includes compilation.

## Development-only modules

CDF97, SPECK2D, OutlierCorrect/Cdf97OutlierCorrect, SZx,
FusedQuantAdaptiveLorenzo, and the legacy SZp
reference implementation are preserved on `development`, alongside research
artifacts, profiling programs, demonstration material, and AMD backend work.
They are unavailable in stable main: no constructors, presets, or archive decoders
for these stages ship in this build. Their historical IDs remain reserved:
36, 37, 39–41, and 43. Existing archives using these IDs require a compatible
`development` decoder; stable main rejects them rather than reinterpreting them.
See the [branch policy](../branch_policy.md) for development and promotion rules.

## Archives and installation

Current archives use FZM 3.1 with checksums and serialized stage configuration.
The reader accepts FZM 3.0 with a warning, subject to stable-catalog stage types and
configurations; this is not a general compatibility promise for every archive
produced by the historical release. Library and archive version numbers are
separate. Newly written archives preserve original input lengths for partial
chunks. Older archives that recorded padded lengths remain readable but return
those stored lengths; missing original lengths cannot be recovered reliably.

Installation exports `FZGMOD::fzgmod` through
`find_package(FZGPUModules REQUIRED)`. Device headers for JIT compilation are
embedded at build time, so relocated installations do not need the source
checkout. CUDA/NVRTC and compatible driver libraries are still required.
See [building and installation](../building.md) for toolkit, C++17, CMake, and
Python requirements.

Module-local CMake declarations, automatic stage scaffolding, and one local/CI
documentation-check command simplify developer integration. The full change
history remains in [CHANGELOG.md](../../CHANGELOG.md).

## Release preparation fixes

Static exports include their utility archive. Sanitizer workflows now execute
registered tests, instrument host code in CUDA files, fail on findings/timeouts,
and preserve diagnostics. ANS header alignment and encoded padding, Huffman
copy lengths, outlier-buffer initialization, empty-input counter state, and
GInterp mode-2 shared-memory ordering were corrected. File decoding now leaves
inverse results under DAG ownership and guards caller output until successful
completion. Previously undefined
padding can change archive bytes without changing the layout or reconstruction.
See the [validation report](v2.0.0-validation.md) for coverage, the unexplained
racecheck stall that passed on rerun, and performance considerations.
